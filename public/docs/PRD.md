# 衣序自然语言衣橱检索与穿搭策略原型

本项目把自然语言需求转为可检查的衣物条件，先检索符合条件的单品，再从个人衣橱生成组合。当前定位为求职作品中的产品与策略原型，验证约束解析、候选筛选、排序与失败处理。示例衣橱和开发评测题为人工构造；真实访谈、盲评与连续试用尚未完成。

2026年11月8日低成本天气版0.2.1已上线，完成105/105项工程回归、真实天气接口、本地与公网天气AI链路及手机尺寸改城市流程验收。工程与链路可用不代表模型质量或用户收益已获验证；具体记录见仓库中的 `docs/weather-ai-delivery.md`。

## 用户与待验证问题

假设目标人群是已有稳定衣橱、会为通勤或具体活动临时选择搭配的人。需要验证的问题是：自然语言表达是否比逐项筛选省力；用户是否愿意维护衣物属性；锁定某件、排除颜色和换一件是否足以帮助决策。年龄、衣橱规模、痛点强度均为待研究假设，不预设已被用户验证。

示例任务是“明天18度通勤，不穿裙子，保留白衬衫”。任务完成应同时包含已表达条件的正确理解、能在衣橱中找到的组合、用户可检查和修改的结果。

天气增量新增的任务假设是：用户选择城市与出行时段后，希望少填一次气温，并能理解气温变化为何影响候选选择。天气展示与自动填温度本身是普通产品功能；AI增量要通过相同天气、衣橱和候选条件下的比较来验证，不能仅因调用模型就宣称推荐更好。

## 当前交付范围

- 自然语言与表单输入场合、气温、颜色禁止、裙裤选择、单品锁定和排除。
- 将理解出的条件显示给用户，支持纠正；多轮只更新被修改的条件。
- 按条件筛选单品，对完整组合先校验再排序；无解不自动放宽。
- 展示候选、理由与权衡；仅引用衣橱中存在的单品。
- 使用人工构造的示例衣橱，支持手动维护数据。
- 区分想穿计划和用户自报实际穿着，保留带日期记录。
- 规则、模型增强和直接模型对照分别标识；模型不可用时明确显示规则回退。

当前不承诺图像理解、真实面料识别、服装专业审美、商品购买、个性化长期学习或在线账号同步。拍照识别为后续可选阶段，未实现时不显示伪造识别结果。天气参考在本次增量范围内，天气准确度、真实穿着舒适度和用户收益尚未验证。

## 天气增量范围与调用成本

天气工具使用 Open-Meteo 托管接口，首版限制为固定15个城市，不获取精确定位。支持今天、明天，以及早晚通勤、白天、晚上、全天等预设时段；以城市时区解释目标日期，展示逐小时预报的时段摘要，不将当天全量预报误称为此刻实况。原始小时数据在单实例内存缓存30分钟，每次重新计算剩余时段；GET天气接口还允许公共CDN缓存最多5分钟并在下个整点前到期。内存缓存不跨实例共享，缓存也不代表天气实时更新。

| 用户动作与版本 | 目标行为 | 模型调用预算 |
|---|---|---:|
| 首页打开或修改天气选择 | 查询天气并按规则生成候选，展示来源和更新时间 | 0次 |
| 主动点击天气AI建议 `weather` | 保留已确认条件，在合格候选上结合天气与偏好重排 | 最多1次 |
| 高级比较 `hybrid` | 模型理解需求，再对合格候选重排；用于比较流程价值 | 有合格候选且两阶段成功时2次 |
| 全量模型对照 `direct` | 仍是高级实验入口，返回衣物必须通过约束校验 | 按实际执行记录 |

预算是流程上限，不是已发生的费用。`meta.modelCalls`统计provider调用尝试数，共享额度拦截时可能未向模型服务发出请求，不是精确计费次数；应同时记录实际阶段、usage和回退。原有共享模型额度限制继续生效，不因天气入口而绕过。首页自动推荐不得暗中调用模型，不能将规则结果标成天气AI成功。

天气结果需要展示城市、目标日期、时段、时区、气温与体感范围、最高降水概率、最大风速、来源、查询时间及缓存状态。用户手动气温优先于自动天气取值，并说明本次使用的温度来源。切换城市或日期后，旧天气和旧推荐立即失效；已确认的裙裤、颜色、锁定与排除条件应保留。

天气接口超时、响应字段缺失或无可用时段时，明确显示天气不可用，继续允许手动气温或已有规则；不得以示例晴天替代真实失败。30分钟缓存过期后获取失败，不可将旧缓存展示为刚取得的新天气。模型异常则回到明确标识的规则结果，保留真实降级原因；缺少天气与缺少模型应分别说明。

## 规则与软偏好

硬约束是衣橱内单品、完整必需品类、用户显式锁定、排除、禁止颜色与裙裤选择。单套含一件上装、一件下装和一双鞋，可有一件外套和一件配饰。品类不足、锁定不存在、锁定与禁止冲突应说明原因。

气温相关厚薄、正式度、配色与近期少重复是演示软偏好，排序分没有外部效度保证。不能把启发式分数写作准确率或穿着适宜性。用户如要严格不穿某件，应使用明确排除；近期降权不会自动把衣橱判为无解。天气、材质等数据不存在的限制应提示不能可靠执行。

天气只提供决策依据，不能自行增加“必须有厚外套”等硬条件，或覆盖明确的禁穿要求。气温低但衣橱薄时，应返回现有可行方案并说明厚薄权衡。降雨概率和风速不能推出衣物具有防水、防风性能；首版未确认这些属性，遇到“必须防水”应明确提示无法确认，不能显示已满足。AI输出的天气建议必须由实际天气字段、已有单品和已确认属性支持，不能把自由生成的材质或性能描述认证为事实。

## 关键路径与验收

| 任务 | 可观察的验收证据 |
|---|---|
| 输入并修改需求 | 显示解析条件；修改温度后保留已确认的裙裤与锁定条件 |
| 检索与组合 | 所有返回ID存在；显式条件全部满足；少于3套时如实展示 |
| 无解处理 | 在全组合空间检查后给诊断，不能只因Top 3失败而断言无解 |
| 不支持条件 | 明确显示局限和下一步操作，不将未知属性当已满足 |
| 模型比较 | 请求版本、实际模式、降级原因和调用记录可核对 |
| 穿着反馈 | 收藏、想穿与实际已穿分别记为不同事件 |
| 天气查询与时间 | 固定城市和城市时区下日期、所选小时、来源与缓存状态正确；失败不显示伪天气 |
| 首页成本 | 自动规则推荐模型调用数为0，网络天气请求与模型请求分别追踪 |
| 天气AI成本 | 主动点击最多一次模型重排；失败实际模式为规则，不能伪称AI已完成 |
| 天气与手动覆盖 | 说明采用手动还是天气温度；改城市/时段不丢掉硬约束，旧推荐不可继续保存 |
| 事实与软偏好 | 不编造防水/防风；低温与不够正式不会误拒可满足任务 |

## 研究与指标阶段

阶段一已建立开发回归题和独立约束检查器，规则37/37、混合策略首轮34/37符合预标期待，具体实测见 `eval/results/rule-report.md` 与 `eval/results/hybrid-report.md`。首轮3个诊断/澄清策略失败修复后，单独定向复验3/3通过，记录在 `eval/results/clarification-fix/`；未做修复后全量复测，不能合写成37/37或宣称模型优于规则。这类题只能支持工程回归结论。

阶段二计划开展访谈和任务观察，核实产品问题与交互；阶段三建立独立检索标注集和模型对比。真实用户人数、效果比例、成本和上线时延均按实际记录，不预填目标成果。详见测评方法和研究模板。

天气增量另外准备 `eval/weather-cases.json` 中的12条人工构造开发场景，使用固定时钟与天气快照检查时间选择、缓存、回退、调用次数和约束保持。文件仍为 `draft_not_run`，尚未通过任务运行器执行；它们与原37条分开，不是独立保留测试，不能据此填写天气通过率或AI提升。天气接口真实连通性、模型真实调用与用户偏好评价分别验收；mock通过不能替代这三类证据。

本机全量 `node --test tests/*.test.js` 已通过105/105，含天气工具13项、服务天气12项、前端6项及天气HTTP边界；这是工程测试，不是上述12条天气任务的已运行成绩。发布前原37题规则新批37/37的公开汇总在 `eval/results/weather-release-rule/`，不覆盖原结果。本地一次真实天气AI返回3套、一次模型重排、服务耗时1631ms、2763token；最终公网0.2.1同样返回3套、一次尝试、无降级，页面显示单次服务耗时约1.14秒。首页规则请求usage为null、模型阶段全false。手机尺寸改城市自动规则更新，保留裙裤与场合条件，未新增模型调用。单次记录不证明模型优于规则，不估算未知单价费用。历史原始响应、日志和截图在本地留存；公开仓库仅提供题库、评测器及分批汇总。

## 产品取舍

选择可维护的小衣橱与显式条件，使结果能够核验，并控制原型范围。使用规则保障硬约束，模型负责可比较的理解与重排；只有实际运行和独立评价才能判断模型是否带来增益。没有为标签增加多智能体或复杂基础设施。
