# 衣序：GitHub 复用调研与天气 AI 改造建议

核查日期：2026-11-08。通过 GitHub 公开页面与 REST API 阅读仓库元数据、README、许可证及下文列出的源码。本文保留实施前调研快照；调研时未安装这些项目或执行第三方代码。后续实际完成的0.2.1天气工作流与本文目标建议分开，见[实施记录](weather-ai-delivery.md)。

## 结论

推荐以现有衣序为基础，调用 Open-Meteo 托管天气 API，参考 Vercel Chatbot 的天气工具和工具结果展示，将真实天气接入现有自然语言解析、候选生成、模型重排与约束校验。Promptfoo 可选用于开发期评测管理。

产品定位可以是“基于实时天气与个人衣橱的场景化推荐助手”。C 端是用户类型，AI 是能力，两者不矛盾。天气接口负责提供事实；模型负责理解口语、结合场景与偏好选择候选、生成有依据的解释。要通过对照评测确定模型是否有额外价值。

## 源码证据及不能照搬的地方

1. [Vercel 的真实天气工具](https://github.com/vercel/chatbot/blob/main/lib/ai/tools/get-weather.ts)：输入城市或经纬度，调用 geocoding API，然后调用 forecast API。现有示例主要取气温与日出日落。衣序还需要体感温度、降水、风速、目标日期/时段、超时和响应检查。它只取首个城市匹配，中文同名城市应另外处理。
2. [Vercel 天气组件](https://github.com/vercel/chatbot/blob/main/components/chat/weather.tsx)：展示逐小时温度。含默认 `SAMPLE` 数据；衣序不能在天气失败时把示例数据当实时天气。须明确显示失败或过期状态。
3. [Outfit Buddy 模拟上下文](https://github.com/iosifidis/outfit-buddy/blob/main/src/services/mockContext.ts)：天气固定为 Thessaloniki、13℃、Rainy；日程固定为 10:00 AM 的 Quarterly Business Review。
4. [Outfit Buddy 穿搭流程](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/flows/suggest-outfit-flow.ts)：导入上述模拟上下文，并传入模型提示词。因此“天气日历联动”在本次检查路径中并非真实外部查询。
5. [Outfit Buddy 衣橱工具](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/tools/get-available-clothing-tool.ts)：处理调用方提供的衣物数组，并可筛选收藏；并非另行检索远程衣橱。
6. [Outfit Buddy 图片识别](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/flows/recognize-item-flow.ts)：有图片输入与结构化属性输出的代码，但未验证可运行性或精度。面料、防水等不能仅凭照片当作已确认事实；当前文本模型配置也不自动意味着支持图片。
7. [Open-Meteo 接口定义](https://github.com/open-meteo/open-meteo/blob/main/openapi/forecast.yml)：已核对 `temperature_2m`、`apparent_temperature`、`precipitation_probability`、`precipitation`、`wind_speed_10m` 和 `timezone`。

## 第一优先级：打开页面即可按当天天气推荐

建议体验：用户首次选择城市与常见出行时间，之后打开“今日穿搭”自动更新天气，并在用户选择 AI 模式时生成建议。无需每天手动输入温度。城市可修改；定位是可选操作，不强制获取精确位置。

例如用户输入：“我在上海，今天早上通勤、晚上约会，怕冷，不穿裙子。”系统应：

1. 解析城市、日期、出行时段、场合、怕冷偏好、禁穿裙子；缺失且影响决策的信息才追问。
2. 查询对应时区与日期的天气，按实际出行小时汇总体感温度范围、降水概率和风速。
3. 检索衣橱并生成符合明确要求的候选；模型结合天气与场合重排，给出可核查的选择理由。
4. 最终再次校验单品是否存在、锁定/排除是否满足，不能由模型自行放宽禁穿条件。
5. 用户说“外套换轻一点”后只更新相关偏好，保留城市、场合与禁穿裙子等已确认信息。

以上是目标体验，不是对今日上海天气的陈述。

用户应看见四类信息：

- **天气依据**：城市、目标日期/时段、数据来源、查询时间、是否缓存；预报和当前天气区分。
- **理解的需求**：通勤、约会、怕冷、不穿裙子等可修改条件。
- **推荐与取舍**：候选单品、天气如何影响选择、有哪些信息未知；理由必须关联实际天气字段与衣物属性。
- **真实执行状态**：查询天气、检索衣橱、生成建议、失败回退。状态来自实际执行记录，不展示伪造的“思考过程”。

固定流程自动调用天气属于 AI 工作流。若要进一步称为工具调用 Agent，应实际实现并记录模型选择工具/参数、接收结果、必要时澄清或继续调用的过程；不能只改名称。

## 最小技术改动与验收

| 交付 | 改动位置建议 | 验收证据 |
|---|---|---|
| 天气适配器 | 新增 `lib/weather.js` | 真实 API 返回、规范化城市与时区、逐小时选择、来源、缓存时间、超时/错误状态 |
| 场景输入 | `lib/core.js`、`lib/llm.js` | 城市/日期/时段保留至推荐阶段；用户修改不会覆盖无关约束 |
| 推荐链路 | `lib/service.js` | 天气摘要实际进入候选评分与模型重排；明确区分实际模型模式和回退 |
| 天气和解释界面 | `public/app.js` 等 | 首页可自动取当天天气；展示真实依据；切换城市和重新推荐可用 |
| 衣物属性 | 衣橱数据及编辑界面 | 防水/防风等关键属性采用已确认是/否/未知；未知不得当作满足“必须防水” |
| 评测交付 | `eval/` 与评测文档 | 固定天气快照、独立判分、版本清单、失败案例与复验结果 |

调研时 `core.js` 主要处理单一温度，雨风诉求仍按不支持处理；仅添加天气卡片不会让推荐自动利用这些信息。改造需要贯穿输入、数据、推荐和输出。后续实现范围以天气实施记录为准。

天气接口失败时保留手动温度入口；缓存过期需要标明。对缺失的天气不能生成“晴天/适合出门”等断言。一般天气适配作为排序偏好；用户明确“必须防水”时按证据处理，避免把所有天气偏好变成强制补齐衣橱的条件。

## 评测：证明 AI 增量价值

建议将天气用例纳入原有独立任务集规划，并单独标记来源和天气快照，不把已有开发题改名为保留测试。先构建覆盖边界的小型开发集，再冻结方案测试未参与调优的题。

对比至少三种设置：

| 设置 | 输入和方法 | 用于回答的问题 |
|---|---|---|
| A | 现有单温度规则版 | 当前基线怎样？ |
| B | 相同逐小时天气 + 规则策略 | 新增天气信息本身带来什么变化？ |
| C | 与 B 相同天气/衣橱/候选池 + 模型重排 | 模型选择是否比规则更适合场景？ |

单独评估自然语言解析；比较重排时使用相同已确认条件和候选池。否则无法把效果变化归因到模型。在线查天气用于连通性验收，重复的策略评测使用冻结天气快照，防止天气随时间变化造成不公平。

重点场景：城市歧义；今天/明天/跨时区；早晚温差；室内办公与室外通勤；怕冷偏好；降雨但鞋子防水属性未知；锁定单品与条件冲突；手动温度覆盖；天气超时/过期缓存；多轮改城市仍保留禁穿条件。

结果至少报告：城市日期与字段解析、工具查询成功/错误、硬约束违规、天气和衣物事实无依据断言、不必要澄清/拒答、人工盲评胜平负、端到端时延、实际调用量及回退比例。小样本披露人数、任务数和原始分母，不写虚构提升。

Promptfoo 可以负责批量执行和结果矩阵；本轮只核对其 README，具体自定义 provider/assertion 对接仍需实施时验证。现有独立约束判分器应保留。云模型评测仍会将输入发送给模型服务，本地运行评测工具不等于所有计算都在本机。

## 第二优先级与简历交付

天气链路完成后，再考虑“拍照录入衣物 → 模型建议类别/颜色 → 用户确认 → 衣橱检索”，以及有数据支撑的偏好反馈。这比同时增加日历授权、AR 试衣或多个 Agent 更容易完成可验收的作品。

面试作品应包含：可访问 Demo、2 分钟演示、工具和推荐链路说明、版本对照报告、3—5 个有证据的失败修复案例。对 AI 搜索/策略/评测岗位，重点讲清查询理解、候选召回与重排、硬约束、事实依据、澄清/降级和实验设计。

实施交付应分别描述已完成的天气工作流与待完成的质量评测。当前0.2.1已上线，完成真实天气和公网AI链路验收；12条固定天气任务仍是待执行规格，尚未完成独立质量对照、用户偏好或改善比例验证，不能将这些计划写成成果。

## 服务与复用边界

- Open-Meteo 当前 README 说明非商业 API 免费且无需 Key；展示数据时按 CC BY 4.0 标明来源。其服务端源码的 AGPL 许可与使用托管 API/数据的条件不同，不能混为一谈。商业用途需另核服务条款。
- SDK/框架开源不代表模型调用免费。继续沿用项目已有调用额度、去重与缓存措施；自动推荐触发应控制刷新次数。
- 按实际复制的文件保留适用版权/许可证/NOTICE，记录来源与修改；不要将开源项目整体包装成自主研发。
- 研究页面快照在本地留存，公开仓库提供上文来源链接与核查结论，不提供私有快照下载。未对中国大陆访问速度、天气准确度或中文城市匹配进行实测。
