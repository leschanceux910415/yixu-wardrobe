# 衣序：GitHub 复用调研与天气 AI 改造建议

核查日期：2026-11-08。调研方式为阅读GitHub公开页面、REST API元数据、README、许可证与列出的源码。本文保留实施前的选型与目标方案，后续0.2.1落地范围见[实施记录](weather-ai-delivery.md)。

## 结论

推荐以现有衣序为基础，调用 Open-Meteo 托管天气 API，参考 Vercel Chatbot 的天气工具和工具结果展示，将真实天气接入现有自然语言解析、候选生成、模型重排与约束校验。Promptfoo 可选用于开发期评测管理。

产品定位为面向个人衣橱的场景化推荐助手。天气工具提供所选时段预报，规则筛选合格组合，模型理解口语并结合场景与偏好选择候选。后续使用相同天气和候选池对比规则与模型排序。

## 源码观察与适配设计

1. [Vercel 的真实天气工具](https://github.com/vercel/chatbot/blob/main/lib/ai/tools/get-weather.ts)：输入城市或经纬度，调用 geocoding API，然后调用 forecast API。现有示例主要取气温与日出日落。衣序还需要体感温度、降水、风速、目标日期/时段、超时和响应检查。它只取首个城市匹配，中文同名城市应另外处理。
2. [Vercel 天气组件](https://github.com/vercel/chatbot/blob/main/components/chat/weather.tsx)：展示逐小时温度并包含默认 `SAMPLE` 数据。衣序实际适配采用接口返回值，失败与过期状态单独展示。
3. [Outfit Buddy 模拟上下文](https://github.com/iosifidis/outfit-buddy/blob/main/src/services/mockContext.ts)：天气固定为 Thessaloniki、13℃、Rainy；日程固定为 10:00 AM 的 Quarterly Business Review。
4. [Outfit Buddy 穿搭流程](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/flows/suggest-outfit-flow.ts)：将上述模拟天气与日程作为模型提示词上下文，可参考场景信息的组织方式。
5. [Outfit Buddy 衣橱工具](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/tools/get-available-clothing-tool.ts)：处理调用方提供的衣物数组，并筛选收藏，可参考本地衣橱工具的输入输出。
6. [Outfit Buddy 图片识别](https://github.com/iosifidis/outfit-buddy/blob/main/src/ai/flows/recognize-item-flow.ts)：提供图片输入与结构化属性输出的实现参考。衣序后续若采用图像录入，可设计模型建议类别/颜色、用户确认属性的流程，并单独验证识别质量。
7. [Open-Meteo 接口定义](https://github.com/open-meteo/open-meteo/blob/main/openapi/forecast.yml)：已核对 `temperature_2m`、`apparent_temperature`、`precipitation_probability`、`precipitation`、`wind_speed_10m` 和 `timezone`。

## 第一优先级：打开页面即可按当天天气推荐

目标体验：用户首次选择城市与常见出行时间，之后打开“今日穿搭”自动更新天气，主动请求AI建议。城市可修改，当前方案采用手动选择城市。

例如用户输入：“我在上海，今天早上通勤、晚上约会，怕冷，不穿裙子。”系统应：

1. 解析城市、日期、出行时段、场合、怕冷偏好、禁穿裙子；缺失且影响决策的信息才追问。
2. 查询对应时区与日期的天气，按实际出行小时汇总体感温度范围、降水概率和风速。
3. 检索衣橱并生成符合明确要求的候选；模型结合天气与场合重排，给出可核查的选择理由。
4. 服务端复核单品ID、锁定、排除和禁穿条件，输出合格组合。
5. 用户说“外套换轻一点”后只更新相关偏好，保留城市、场合与禁穿裙子等已确认信息。

该示例用于说明城市、时段、场合与偏好的输入结构。

用户应看见四类信息：

- **天气依据**：城市、目标日期/时段、数据来源、查询时间、是否缓存；预报和当前天气区分。
- **理解的需求**：通勤、约会、怕冷、不穿裙子等可修改条件。
- **推荐与取舍**：候选单品、天气如何影响选择、有哪些信息未知；理由必须关联实际天气字段与衣物属性。
- **执行状态**：天气查询、衣橱检索、模型重排与失败回退，由对应执行阶段生成。

当前方案采用固定天气工作流。模型自主选择工具可作为后续实验，记录工具与参数选择、结果接收、澄清及继续执行过程。

## 最小技术改动与验收

| 交付 | 改动位置建议 | 验收证据 |
|---|---|---|
| 天气适配器 | 新增 `lib/weather.js` | 真实 API 返回、规范化城市与时区、逐小时选择、来源、缓存时间、超时/错误状态 |
| 场景输入 | `lib/core.js`、`lib/llm.js` | 城市/日期/时段保留至推荐阶段；用户修改不会覆盖无关约束 |
| 推荐链路 | `lib/service.js` | 天气摘要实际进入候选评分与模型重排；明确区分实际模型模式和回退 |
| 天气和解释界面 | `public/app.js` 等 | 首页可自动取当天天气；展示真实依据；切换城市和重新推荐可用 |
| 衣物属性 | 衣橱数据及编辑界面 | 防水/防风等属性采用已确认是/否/待确认，缺失时进入确认流程 |
| 评测交付 | `eval/` 与评测文档 | 固定天气快照、独立判分、版本清单、失败案例与复验结果 |

调研时 `core.js`主要使用单一温度，雨风需求进入澄清流程。天气改造贯穿输入、数据、推荐和结果解释，实际落地范围记录在天气实施文档中。

天气失败时保留手动温度入口，缓存过期显示状态；天气因素参与排序，用户明确提出防水等条件时根据已确认衣物属性检查，缺失属性进入确认流程。

## 模型增量评测方案

天气任务单独标记来源和快照；开发集覆盖工具、约束与异常，保留集按需求家族和衣橱快照另行构建，冻结方案后运行。

对比至少三种设置：

| 设置 | 输入和方法 | 用于回答的问题 |
|---|---|---|
| A | 现有单温度规则版 | 当前基线怎样？ |
| B | 相同逐小时天气 + 规则策略 | 新增天气信息本身带来什么变化？ |
| C | 与 B 相同天气/衣橱/候选池 + 模型重排 | 模型选择是否比规则更适合场景？ |

自然语言解析单独评估，重排比较固定已确认条件与候选池。在线查询用于接口连通性验收，策略实验采用冻结天气快照，控制时序数据变化。

重点场景：城市歧义；今天/明天/跨时区；早晚温差；室内办公与室外通勤；怕冷偏好；降雨但鞋子防水属性未知；锁定单品与条件冲突；手动温度覆盖；天气超时/过期缓存；多轮改城市仍保留禁穿条件。

结果记录城市日期与字段解析、工具查询状态、硬约束违规、无依据断言、不必要澄清、人工盲评胜平负、端到端时延、实际调用量与回退比例，同时保存人数、任务数和分母。

Promptfoo可用于批量执行与结果矩阵，当前核查到README层面，provider/assertion对接列为可选工程任务。现有运行器在本地执行，模型阶段调用服务接口，独立约束判分器继续负责结果检查。
