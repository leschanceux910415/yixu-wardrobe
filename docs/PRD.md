# 衣序产品需求说明

衣序将自然语言需求转为可修改的衣物条件，从个人衣橱中检索单品、生成组合并解释取舍。当前0.2.1版本已上线，完成105/105项工程回归、真实天气查询、本地与公网天气AI链路验收。页面使用24件人工构造示例衣物，开发回归另用12件评测衣物。

## 目标任务与研究问题

目标场景是通勤与具体活动前的穿搭选择。示例任务：“明天18度通勤，不穿裙子，保留白衬衫。”用户确认条件后，可查看候选、锁定单品、排除某件或局部换件。

产品研究围绕三个问题开展：自然语言输入能节省多少筛选操作；用户维护衣物信息的成本如何；天气、场合和个人偏好如何影响选择。下一阶段计划通过访谈、任务观察与连续试用获得反馈。

天气流程让用户选择城市与出行时段，自动获得温度参考。模型排序价值将通过相同天气、衣橱、条件和候选池的对照实验评估。

## 当前功能

- 自然语言与表单输入场合、气温、禁穿颜色、裙裤选择、锁定和排除。
- 展示可纠正的条件摘要，多轮修改保留其余已确认条件。
- 枚举组合、检查显式约束、排序展示；无解时给出具体冲突与恢复操作。
- 支持手动维护衣物信息，缺失材质、防水等属性显示为待确认。
- 分别保存想穿计划与用户自报已穿记录，采用浏览器本地存储。
- 展示请求版本、实际生成模式、执行阶段与回退原因。

当前采用手动衣物录入与固定流程编排。图像录入、云端账号同步和长期偏好学习列为后续扩展方向。

## 天气与模型流程

天气工具调用Open-Meteo托管接口，提供固定15城、今天/明天，以及早晚通勤、白天、晚上、全天等预设时段。日期与小时按城市时区解释，界面展示所选时段的预报摘要、来源与查询时间。

| 用户动作 | 流程 | 模型预算 |
|---|---|---:|
| 打开首页或修改天气 | 查询天气，生成规则候选 | 0次 |
| 主动点击天气AI `weather` | 保留已确认条件，在合格候选中重排 | 最多1次 |
| 高级比较 `hybrid` | 模型理解需求，再重排合格候选 | 两阶段均执行时2次 |
| 全量衣橱对照 `direct` | 模型生成结果，服务端执行约束复核 | 按实际阶段记录 |

`meta.modelCalls`记录provider调用尝试，实际阶段、usage和回退分别保存。公开部署使用共享额度服务，当前Demo每日模型调用额度为100次；额度服务异常或模型请求失败时采用规则结果。

原始小时预报在单实例内存缓存30分钟，每次重算时段摘要；公共天气GET允许最多5分钟CDN缓存，并在下个整点前到期。界面保留原始获取时间与缓存状态。过期后查询失败则进入天气不可用状态，用户可继续手动指定气温。

用户手动温度优先于自动天气取值。切换城市、日期或时段后使旧结果失效，并保留裙裤、禁穿颜色、锁定与排除条件。

## 约束与模型职责

确定性模块负责可行性：单品来自衣橱，组合包含必需品类，并满足显式锁定、排除、颜色与裙裤要求。单套含一件上装、一件下装和一双鞋，可选外套及配饰。品类缺失、锁定冲突或条件冲突分别返回诊断。

厚薄、正式度、配色与近期重复参与软偏好排序。低温或正式场合下，系统保留现有可行组合并说明偏好取舍；用户明确排除的单品则进入硬条件检查。

模型负责需求理解与候选选择，服务端复核输出ID和完整组合。天气建议采用结构化建议代码，由已获取的天气字段与衣物属性核验后映射为文案。材质、防水、防风等缺失属性走确认或澄清流程。

## 关键验收

| 任务 | 验收内容 |
|---|---|
| 输入与修改需求 | 条件摘要准确，修改温度后保留已确认裙裤与锁定条件 |
| 检索与组合 | 返回ID存在、品类完整、显式条件满足，展示实际可行套数 |
| 无解诊断 | 在受限枚举空间完成可行性检查，并给出具体恢复操作 |
| 属性待确认 | 明确标记缺失信息并提供下一步确认入口 |
| 模型执行 | 请求版本、实际模式、回退与阶段记录对应 |
| 穿着记录 | 收藏、想穿与自报已穿采用不同事件 |
| 天气时间 | 城市、日期、时区、小时范围、来源与缓存状态对应 |
| 自动推荐成本 | 首页与天气切换的模型调用数为0 |
| 天气AI成本 | 主动请求最多一次候选重排，失败切回规则 |
| 状态更新 | 改城市或时段保留硬条件，并使旧推荐失效 |
